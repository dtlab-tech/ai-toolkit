# Technical Specification — Atomic Work Breakdown

## Document Info
| Field | Value |
|-------|-------|
| Feature | FTR-014 — Atomic Work Breakdown |
| Version | 1.0 |
| Date | 2026-08-05 |
| Status | Draft |

## 1. Overview

FTR-014 redefines the task as the smallest independently implementable, verifiable, and committable unit of work. It introduces:

1. **Structured JSON schema (v2)** — the authoritative work breakdown source, replacing CSV as single source of truth
2. **Two-stage validation pipeline** — deterministic JavaScript module (`.claude/scripts/wb-validate.js`) for structural checks, followed by semantic LLM validation (`validate-work-breakdown-semantic` agent) for coherence analysis
3. **Deterministic rendering** — JavaScript module (`.claude/scripts/wb-render.js`) that produces Markdown and CSV from JSON
4. **Atomic task contract** — each task declares exactly one observable outcome, one domain, one agent type, with verification commands and estimates targeting ≤15 minutes per task
5. **Upgraded Gate 2** — blocks on structural errors, tasks >30 minutes, semantic findings, or uncovered Must-priority acceptance criteria; presents four-band duration statistics

The pipeline addresses a real delivery problem: unconstrained task sizes led to 8.9x token overruns, multi-cycle rework, and cascading failures. Fine-grained atomicity with explicit verification and time bounds isolates failures to the task level.


## 3. Backend

### 3.1 Work Breakdown JSON Schema (v2)

**File:** `{PREFIX}-Work-Breakdown.json`  
**Purpose:** Authoritative task specification; sole source of truth for task identity, relationships, estimates  
**Generated by:** `generate-work-breakdown` agent (haiku)  
**Consumed by:** `wb-validate.js`, `validate-work-breakdown-semantic`, `wb-render.js`, Gate 2 payload assembly

**Schema structure (TypeScript for clarity):**

```typescript
interface WorkBreakdownV2 {
  schemaVersion: 2;
  feature: string;  // e.g. "FTR-014"
  phases: Phase[];
}

interface Phase {
  id: string;  // "INFRA" or "US-01" etc
  type: "infrastructure" | "user-story";
  title: string;  // must not contain |, CR, LF
  commit: CommitMetadata;
  tasks: Task[];
}

interface CommitMetadata {
  type: string;    // "feat", "refactor", etc (conventional commit)
  subject: string; // no prefix; must not contain |, CR, LF
}

interface Task {
  id: string;  // INFRA-TASK-{DOMAIN}-{NN} or {US-ID}-TASK-{DOMAIN}-{NN}
  title: string;  // must not contain |, CR, LF
  outcome: string;  // single observable outcome statement
  domain: "BE" | "FE" | "DB" | "DevOps" | "INFRA" | "TEST";  // whitelist
  agentType: string;  // "developer-backend" | "developer-frontend" | "developer-testing"
  dependsOn: string[];  // task IDs this depends on; may be empty
  acceptanceCriteria: string[];  // AC IDs from Requirements; may be empty
  verification: {
    commands: string[];  // non-empty array of shell commands
  };
  estimate: {
    agentMinutes: number;  // positive integer; targeting ≤15
    tokens: number;  // non-negative integer
  };
  outputCount: number;  // positive integer
  groupingRationale: string | null;  // required if outputCount > 1
  commit: CommitMetadata;
}
```

**JSON serialization:**
- UTF-8 encoding
- 2-space indentation (for human readability and diffs)
- No trailing newline (Node.js convention)

### 3.2 Acceptance Criteria Source — **RESOLVED: Option A**

**Status:** Resolved — selected before Gate 1 as required.

**Decision:** Option A — JavaScript parsing of the `## 7. Acceptance Criteria` section of `{PREFIX}-Requirements.md`.

**Rationale:** Requirements.md is generated by `generate-requirements` (which already follows a fixed table format) and is stable within a feature delivery run. Option B would require pipeline changes outside this feature's scope; Option C would add a subprocess boundary with no benefit over inline parsing.

**Full parsing contract for `wb-validate.js`:**

1. Read `{PREFIX}-Requirements.md` as UTF-8 text
2. Locate the section starting with the exact line `## 7. Acceptance Criteria`; abort with exit code 2 if not found
3. Find the first Markdown table after that heading (recognizable by a header row containing `| ID |`); abort with exit code 2 if not found or table has fewer than 3 columns
4. Verify columns are: `ID` (col 1), `Criterion` (col 2), `Related UC` (col 3); abort with exit code 2 if columns are missing or out of order
5. Parse each data row (skip header row and separator row `|---|...|`); trim whitespace from each cell
6. For each row, extract:
   - **ID** (col 1): the AC identifier, e.g. `AC-01`; abort with exit code 2 if duplicate AC ID found
   - **Criterion** (col 2): human-readable text (not used for validation logic)
   - **Related UC** (col 3): one or more UC-NN values (comma-separated), or the literal `All UCs`
7. Parse `Related UC`:
   - If the value is `All UCs` (case-insensitive trim): mark the AC as `unscoped: true`; `allowedUserStories: []` (all)
   - Otherwise: split by comma, trim each token, expect each to match `UC-\d+`; abort with exit code 2 if any token is malformed
   - Map each `UC-NN` to the corresponding `US-NN` (e.g., `UC-02` → `US-02`); abort with exit code 1 if any `UC-NN` does not exist in the feature's Use Case list
8. Derive **priority** from the referenced UC(s):
   - For each `UC-NN`, look up the priority of that Use Case in the Requirements document (expected in the UC metadata table: `| Priority | Must |`)
   - If the UC has no declared priority, abort with exit code 1 (explicit error: "UC-NN has no declared priority")
   - When multiple UCs are referenced, use the strongest priority: `Must > Should > Could`
9. Build the in-memory index:
   ```
   Map<acId, {
     id: string,
     priority: "Must" | "Should" | "Could",
     allowedUserStories: string[],  // empty means unscoped
     unscoped: boolean
   }>
   ```
10. After processing all rows, validate:
    - No AC ID appears more than once → exit code 2 if duplicate
    - All referenced UC-NN values exist → exit code 1 if any not found
    - All referenced UC-NN values have a declared priority → exit code 1 if any missing

**Requirements table format (as generated by `generate-requirements`):**

```markdown
## 7. Acceptance Criteria

| ID | Criterion | Related UC |
|----|-----------|-----------|
| AC-01 | Given ... when ... then ... | UC-01 |
| AC-02 | Given ... when ... then ... | UC-01, UC-02 |
| AC-03 | Given ... when ... then ... | All UCs |
```

**Use Case priority source (parsed from each UC's metadata table in Requirements):**

```markdown
### UC-01: ...

| Field | Value |
|-------|-------|
| Priority | Must |
```

**Note:** The `generate-requirements` agent must produce the AC table in this exact format and UC metadata tables with a `Priority` field. Any deviation causes `wb-validate.js` to abort with exit code 2.

**LLM extraction is explicitly prohibited** — all AC metadata is extracted deterministically from these table structures.

### 3.3 Validation Modules

#### 3.3.1 `.claude/scripts/wb-validate.js` — Deterministic Structural Validator

**Purpose:** Perform deterministic checks on Work Breakdown JSON; no LLM involved

**Invocation:**
```bash
node .claude/scripts/wb-validate.js <path-to-work-breakdown.json> <path-to-requirements.md>
```

**Inputs:**
- `Work-Breakdown.json` file path (positional arg 0)
- `Requirements.md` file path (positional arg 1) — always `.md` (Option A resolved in Section 3.2)

**Output (stdout):**
```json
{
  "valid": boolean,
  "schemaVersion": 2,
  "taskCount": number,
  "errors": [
    {
      "category": "unique_id_violation" | "missing_field" | "invalid_domain" | "dependency_not_found" | "task_self_dependency" | "task_phase_mismatch" | "task_cycle_detected" | "phase_dependency_not_found" | "phase_cycle_detected" | "phase_unschedulable" | "split_required" | "no_grouping_rationale" | "no_verification_commands" | "no_commit_subject" | "ac_not_found" | "ac_wrong_us" | "ac_invalid_uc_ref" | "uc_missing_priority" | "must_ac_uncovered" | "forbidden_characters",
      "severity": "error",
      "taskId": string,  // nullable for global errors (e.g., schema version)
      "field": string,  // nullable
      "message": string,
      "details": object  // category-specific details
    }
  ],
  "warnings": [
    {
      "category": "duration_warning",
      "severity": "warning",
      "taskId": string,
      "field": "estimate.agentMinutes",
      "message": "Task estimated 21–30 minutes (warning band)",
      "details": {
        "estimateMinutes": number,
        "band": "warning"
      }
    }
  ],
  "durationBands": {
    "target": number,      // ≤15 min
    "aboveTarget": number, // 16–20 min
    "warning": number,     // 21–30 min
    "splitRequired": number // >30 min
  },
  "domainDistribution": {
    "BE": number,
    "FE": number,
    "DB": number,
    "DevOps": number,
    "INFRA": number,
    "TEST": number
  },
  "dependencies": {
    "taskGraph": { "taskId": ["taskId"] },   // task-level adjacency list
    "taskCycles": [["US-01-TASK-BE-01", "US-01-TASK-BE-02"]] | [],  // cycle members if any
    "phaseGraph": { "phaseId": ["phaseId"] }, // phase-level adjacency list (computed projection)
    "phaseCycles": [["US-01", "US-02"]] | [], // phase cycle members if any
    "phaseUnschedulable": ["phaseId"] | []    // phases that buildWaves cannot consume
  }
}
```

**Exit codes:**
- `0` — validation passed (no blocking errors)
- `1` — validation failed (one or more blocking errors)
- `2` — runtime error (e.g., file not found, JSON parse error)

**Checks performed (in order):**

1. **JSON well-formedness** — valid JSON; exits 2 if not
2. **Schema version** — must be exactly 2; error if not
3. **Unique IDs** — all task IDs unique at feature level; error if duplicates found
4. **Required fields** — all task and phase fields present and non-null; error if missing
5. **Task ID format** — matches `INFRA-TASK-{DOMAIN}-{NN}` or `{US-ID}-TASK-{DOMAIN}-{NN}`; error if malformed
6. **Domain whitelist** — domain value in {BE, FE, DB, DevOps, INFRA, TEST}; error if not
7. **AgentType validation** — agentType value in {developer-backend, developer-frontend, developer-testing}; error if not
8. **Task dependency resolution** — all task IDs in `dependsOn[]` exist in the feature; category `dependency_not_found`
9. **Task self-dependency** — no task may appear in its own `dependsOn`; category `task_self_dependency`
10. **Task ID / phase consistency** — a task with prefix `INFRA-TASK-*` must be in the INFRA phase; a task with prefix `{US-ID}-TASK-*` must be in the `{US-ID}` phase; category `task_phase_mismatch`
11. **Task cycle detection** — DFS with gray/black coloring over the full task graph; report all members of each cycle; category `task_cycle_detected`
12. **Phase dependency projection** — compute the phase-level `depends_on` graph using the same algorithm as `wb-render.js` (union task deps → map to owner phase → remove self); verify all referenced phase IDs exist; category `phase_dependency_not_found`
13. **Phase cycle detection** — DFS over the phase graph; report all phase members of each cycle; category `phase_cycle_detected`
14. **Phase schedulability** — run the same `buildWaves` algorithm as `pm-phase3` over the phase graph; if any phase cannot be consumed (remains unscheduled after exhausting wave passes), flag it; category `phase_unschedulable`
15. **Duration policy** — categorize tasks into four bands; flag >30 min as error (splitRequired), 21–30 min as warning, 16–20 min as above target, ≤15 min as target
16. **Verification commands** — verification.commands non-empty and all entries non-empty strings; error if not
17. **Commit subject** — commit.subject non-empty; error if not
18. **OutputCount rationale** — if outputCount > 1, groupingRationale must be non-null; error if not
19. **AC references** — each AC ID in acceptanceCriteria[] exists in the Requirements AC table (parsed per Section 3.2 contract); category `ac_not_found`
20. **AC scope** — task's US must be in the AC's `allowedUserStories` (derived from `Related UC`); unscoped ACs are universally permitted; category `ac_wrong_us`; non-existent UC references in `Related UC`: category `ac_invalid_uc_ref`; UC with no declared priority: category `uc_missing_priority`
21. **Must AC coverage** — every AC with derived priority Must must be referenced by at least one task in the feature; error if uncovered
22. **Text field characters** — phase.title, task.title, commit.subject must not contain `|`, CR (`\r`), LF (`\n`); error if found
23. **Empty phase** — each phase must have at least one task; error if phase is empty

**No external API calls; no network I/O; no subprocess spawning.**

#### 3.3.2 `validate-work-breakdown-semantic` — LLM Semantic Validator Agent

**Purpose:** Analyze coherence and scope quality; detect hidden multiplicity, scope creep, estimation misalignment

**Agent definition:** New agent in `.claude/agents/validate-work-breakdown-semantic.md`

**Model:** Sonnet (haiku is too weak for detailed analysis)

**Inputs:**
- `{PREFIX}-Work-Breakdown.json` (read from feature directory)
- `{PREFIX}-Requirements.md` (read from feature directory)

**Output (to stdout as JSON):**
```json
{
  "valid": boolean,
  "findings": [
    {
      "taskId": "US-01-TASK-BE-01",
      "type": "hidden_multiplicity" | "scope_creep" | "estimate_incompatible" | "bundled_verifiable" | "other",
      "severity": "error" | "warning",
      "blocking": boolean,
      "splitRequired": boolean,
      "description": "Human-readable explanation"
    }
  ]
}
```

**Precondition:** Must only be invoked if `wb-validate.js` exits 0 (no structural errors)

**Analysis categories:**

| Finding Type | Description | Example | Blocking? |
|---|---|---|---|
| `hidden_multiplicity` | Title/outcome uses "N", "all", "complete" suggesting multiple behaviors | "Implement all CRUD operations" | Yes (splitRequired: true) |
| `scope_creep` | Task scope misaligned with assigned US | Task in US-01 but implements feature from US-02 | Yes (splitRequired: false if fixable by reassignment) |
| `estimate_incompatible` | Duration estimate unrealistic for scope | 5-minute estimate for "implement authentication" | Yes if severe; false if minor |
| `bundled_verifiable` | Multiple independently verifiable outcomes in one task | "Add API endpoint and write unit tests" without clear boundary | Yes (splitRequired: true) |
| `other` | Any other coherence issue | — | Varies |

**Decision logic:**
- `blocking: true` + `splitRequired: true` → task must be split
- `blocking: true` + `splitRequired: false` → scope correction needed (e.g., move to different US)
- `blocking: false` → advisory only; Gate 2 not blocked
- `valid: false` when any finding has `blocking: true`

**Phase-level depends_on calculation:**

For each phase, compute once (apply to all rows of that phase):

```
1. Collect all task IDs from task.dependsOn across ALL tasks in the phase
2. For each collected task ID, look up its owner phase from task.id prefix
3. Remove current phase.id from the set (intra-phase deps are implicit in CSV format)
4. Deduplicate and sort alphabetically
5. Join with space → depends_on value
```

**Example calculation:**

```
Phase US-01 has tasks:
  US-01-TASK-DB-01: dependsOn = []
  US-01-TASK-BE-01: dependsOn = ["INFRA-TASK-BE-01"]
  US-01-TASK-BE-02: dependsOn = ["US-01-TASK-BE-01"]  (intra-phase)

Collect: ["INFRA-TASK-BE-01"]
Owner phases: ["INFRA"]
Remove US-01: ["INFRA"]
Join: "INFRA"

CSV rows (all three tasks):
  US-01|...|...|INFRA|US-01-TASK-DB-01|...|DB|developer-backend
  US-01|...|...|INFRA|US-01-TASK-BE-01|...|BE|developer-backend
  US-01|...|...|INFRA|US-01-TASK-BE-02|...|BE|developer-backend
```

**Defensive character stripping:**

Before writing CSV, strip any `|` (pipe), CR (`\r`), LF (`\n`) from:
- `phase_title`
- `task_title`
- `commit_message`

(These should have been rejected by `wb-validate.js`, but strip defensively as a safety net.)

### 3.7 Mapping / Transformations

**Task-level to phase-level dependency mapping (wb-render.js):**

For each phase, union all `task.dependsOn` IDs, map to owner phases, remove current phase, deduplicate, join with space.

This is a **deterministic but intentionally lossy transformation**: task-level intra-phase dependency order is collapsed into a binary phase-level dependency (phase A depends on phase B, or not). `pm-phase3` plans execution at phase granularity, not task granularity, so finer task ordering within a phase is not preserved in the CSV.

**Phase-level dependency graph validation (performed by `wb-validate.js` — not just at task level):**

After building the phase-level aggregate (the same computation as wb-render.js will perform), `wb-validate.js` also checks:
1. **No phase cycles** — the phase-level `depends_on` graph must be acyclic (phases cannot form a cycle)
2. **Phase schedulability** — applying pm-phase3's `buildWaves` algorithm must consume all phases without remainder; any phase that cannot be scheduled (no predecessors satisfy) is flagged as `phase_unschedulable`

These checks are in addition to task-level cycle detection (check 11) and task ID/phase consistency (check 10). All four graph validation layers (task cycle, task ID/phase consistency, phase cycle, phase schedulability) must pass for exit code 0.

   - Acyclic graph passes validation

8. **Phase graph — projection, cycles, schedulability**
   - Phase-level `depends_on` aggregate computed correctly (same as wb-render.js)
   - Phase self-dependency detected
   - Phase cycle detected (US-01 → US-02 → US-01)

   - Unschedulable phase detected and reported

8. **Duration policy**
   - Tasks ≤15 min categorized as "target"
   - Tasks 16–20 min categorized as "above target"
   - Tasks 21–30 min flagged as "warning" (non-blocking)
   - Tasks >30 min flagged as "split required" (blocking error)

9. **Verification commands**
   - Non-empty commands[] accepted
   - Empty array rejected
   - Empty string in array rejected
   - Various command formats accepted (npm test, dotnet build, custom scripts)

10. **Commit subject validation**
    - Non-empty subject accepted
    - Null or empty rejected
    - Pipe character rejected (for CSV safety)

11. **OutputCount rationale**
    - outputCount 1: groupingRationale null or empty is fine
    - outputCount >1: groupingRationale must be non-null and non-empty
    - Missing or null rationale when needed = error

    - CR `\r` character rejected
    - LF `\n` character rejected
    - Clean text accepted
    - Error message includes field name and character

14. **Empty phase**
    - Phase with no tasks rejected

15. **Command result contract, exit codes, and ledger**

    *Exit code routing (wb-validate):*
    - Exit 0 + valid=true → ledger `done`; semantic and render proceed
    - Exit 1 + valid=false → ledger `done`; semantic skipped (`skipped`); render skipped (`skipped`); Gate 2 blocked
    - Exit 2 (runtime error) → throws; ledger `failed`; semantic skipped; render skipped; Gate 2 blocked
    - Exit null/unexpected → throws; ledger `failed`; pipeline blocked
    - Exit 0 + valid=false → throws (inconsistency); ledger `failed`
    - Exit 1 + valid=true → throws (inconsistency); ledger `failed`
    - Empty stdout (any exit) → throws; ledger `failed`
    - Non-JSON stdout → throws (JSON.parse error); ledger `failed`

    *Semantic validator:*
    - Technical failure → render skipped (`skipped`); Gate 2 blocked with error; ledger `failed` with actual tokens consumed
    - Blocking findings → render proceeds; Gate 2 blocked; ledger `done`

    *Renderer (wb-render):*
    - Exit non-zero → `_exitCode` on throw; `renderResult?.exitCode` also set; catch records actual exit code; Gate 2 blocked
    - markdownPath missing from result → throw has no `_exitCode`; `renderResult?.exitCode = 0`; catch records `exit_code: 0`
    - csvPath missing from result → same; catch records `exit_code: 0`
    - markdownExists=false → throw carries `_exitCode: 0`; catch records `exit_code: 0`
    - csvExists=false → same; `exit_code: 0`
    - Agent exception before renderResult received → `renderResult` is null; catch records `exit_code: null`
    - renderFailed → gate2BlockedReasons includes renderer failure message
    - General rule: script ran and result received → record exit code even if 0; exception before result → `null`

    *Exit code propagation (wb-validate):*
    - Exit 2 → `_exitCode: 2` on throw AND `validateExitCode = 2`; catch records `exit_code: 2`
    - Unexpected exit code (e.g., 99) → `_exitCode: 99` on throw AND `validateExitCode = 99`; catch records `exit_code: 99`
    - Exit 0, empty stdout → `validateExitCode = 0`; throw has no `_exitCode`; catch records `exit_code: 0`
    - Exit 1, empty stdout → `validateExitCode = 1`; catch records `exit_code: 1`
    - Exit 0 or 1, non-JSON stdout → `validateExitCode` set; JSON.parse throws; catch records actual exit code
    - Exit 0 + valid=false (consistency guard) → `validateExitCode = 0`; catch records `exit_code: 0`
    - Exit 1 + valid=true (consistency guard) → `validateExitCode = 1`; catch records `exit_code: 1`
    - Agent exception before command result received (timeout, schema mismatch) → `validateExitCode` remains `null`; catch records `exit_code: null`
    - General rule: script ran and returned a result → record the exit code it returned, even if 0; agent exception before result → `null`

    *Token attribution:*
    - wb-validate `done`: ledger phase_delta_tokens = actual tokens consumed
    - wb-validate `failed`: ledger phase_delta_tokens = actual tokens consumed up to failure (non-zero if agent ran)
    - semantic `done`: ledger phase_delta_tokens = actual tokens consumed
    - semantic `failed`: ledger phase_delta_tokens = actual tokens consumed (non-zero if agent ran)
    - Any `skipped`: ledger phase_delta_tokens = 0

    *Ledger error fields (failed entries):*
    - error_summary populated for: command error, timeout, schema mismatch, empty stdout, exit/valid inconsistency, missing markdownPath/csvPath, markdownExists=false, csvExists=false, agent exception
    - exit_code set from `err._exitCode` when throw carried it; null for exceptions with no attached exit code
    - All failed entries have completed_at set

    - `ac_invalid_uc_ref` is NOT triggered for `All UCs`
    - NFR-00 traceability appears in AC criterion text, not in Related UC column

## 12. Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
|---|---|---|---|
| Requirements.md AC section format changes and breaks parser | wb-validate.js AC parser fails silently or with cryptic errors; AC validation skipped or incorrect | Medium | Standardize the `## 7. Acceptance Criteria` table format and UC metadata table format in AGENTS.md; document expected format in `generate-requirements` agent; add parser unit tests covering all known format variations (extra columns, merged cells, different heading levels). |
| wb-validate.js performance regression on large features | Validation >1s on 100+ tasks; bottleneck on Gate 2 | Low | Task graph validation and phase graph projection/schedulability are O(V+E) algorithms (efficient). Profile with 100-task feature; set performance budget to <1s. No lazy evaluation possible (must check all constraints). |
| CSV depends_on aggregation incorrect | pm-phase3 wave planning wrong; incorrect execution order | Medium | Regression test: parse generated CSV, rebuild waves using pm-phase3 logic, verify against JSON intent. Test with >5 cross-phase dependencies in one phase. |
| Pipe characters in task title cause CSV corruption | CSV unparseable by pm-phase3 | Low | wb-validate.js rejects pipes; wb-render.js strips defensively. Test CSV parsing with intentional pipes (pre-filter) to verify safety net. |
| Semantic validator runs on malformed JSON | Wasted token spend on unvalidatable WB | Low | Precondition enforced: semantic agent only runs if wb-validate.js exits 0. No fallback needed. |
| Gate 2 payload too verbose for human review | Stakeholders overwhelmed; poor decisions | Medium | Limit payload to key stats, top 3 findings, critical tasks. Provide summary section highlighting why Gate 2 is blocked (if blocked). Reference full reports for detailed review. |
| Task splitting advice incomplete | Tasks split but still >15 min; Gate 2 needs re-run | Medium | Semantic validator provides splitRequired flag; includes guidance. Recommend two more iterations if split needed. Set expectation that MVP may need two Gate 2 submissions. |
| FTR-015 (Execution Ledger) depends on stable task IDs | Ledger cannot reference tasks if IDs change post-Gate-2 | Low | Freeze JSON after Gate 2 approval. Do not allow task ID changes. If re-planning needed, generate new JSON, re-run validators, new Gate 2. Document this constraint clearly. |
| pm-phase3 continues reading CSV indefinitely | CSV becomes unmaintained; JSON diverges | Low | Schedule FTR-020 (JSON-native pm-phase3) in next sprint. Mark CSV as "temporary" in docs. Maintain consistent rendering (wb-render.js) as single source of truth. |
| Testing coverage insufficient for validators | Bugs slip into production; Gate 2 blocks incorrectly | Medium | Aim for >90% line coverage in wb-validate.test.js. Test all 19 validation checks. Test all error categories. Run `npm test -- --coverage` and review gaps before merging. |

## Summary of Key Decisions

1. **Authoritative source:** JSON schema v2 (not CSV)
2. **Validation approach:** Two-stage (deterministic JS + semantic LLM)
3. **Task contract:** Atomic — one outcome, one domain, one agent type per task
4. **Verification:** Explicit commands required for every task
5. **Duration targets:** ≤15 min target; 21–30 min warning (non-blocking); >30 min error (blocking)
6. **AC validation:** AC IDs must exist in Requirements, belong to task's US (or unscoped), every Must AC covered
7. **AC source:** Option A — JS parsing of `## 7. Acceptance Criteria` table in Requirements.md (see Section 3.2)
8. **Script distribution:** Validators and renderer in `.claude/scripts/` (installed by `install-toolkit`); NOT in `bin/`
9. **Conditional rendering:** wb-render.js runs only if wb-validate.js exits 0
10. **Ledger tracking:** All new agents (wb-validate, semantic, wb-render) tracked in token ledger
11. **CSV retention:** Temporary compatibility layer for pm-phase3; deprecated in FTR-020
12. **Gate 2 enhancement:** Presents four-band stats, semantic findings, uncovered ACs, blocking reasons
