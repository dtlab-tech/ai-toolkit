### UC-03: Apply the accepted split or continue unchanged

| Field | Value |
|-------|-------|
| Actor | User; `implement-feature` main loop |
| Preconditions | `pm-phase1` returned `split_checkpoint` with `status: "split-proposed"` and a `proposal` (UC-01, UC-02). The parent feature folder holds the generated Requirements and Tech-Spec. The user has not yet answered the proposal. |
| Trigger | The user answers the proposal presented in UC-02 with an explicit accept or reject. |
| Priority | Must |

**Main flow:**
1. `implement-feature` Step 1a receives `split_checkpoint` with `status: "split-proposed"` and shows the proposal (UC-02).
2. The user edits the proposal if needed (UC-02) and then gives an explicit written accept. No file or child is created before this confirmation (BR-01).
3. The main loop calls `apply` from FTR-035 with the accepted proposal, as edited in step 2, and the parent's `--prefix`.
4. `apply` creates the child features and registers them as defined by the FTR-035 apply and registry contracts. The parent receives no Gate 1 in this run.
5. The main loop reports to the user the parent's prefix and the child IDs and folders that `apply` created.
6. The pipeline stops for the parent. No Gate 1 digest is produced for the parent in this run.

**Alternative flows:**
- User rejects the proposal → the pipeline continues to Gate 1 with the parent's documents unchanged, and nothing is stored (D-10). No rejection record is written.
- User edits the proposal and then rejects it → treated as a rejection: Gate 1 is reached unchanged and the edits are discarded.
- Session ends before the user answers → the pipeline is not advanced and nothing is stored, because `check-size` only measures and prints (D-05). A later run starts again from the beginning: `check-size` re-measures the documents and builds a new proposal with fresh child IDs.

**Error flows:**
- `apply` fails before any child is created → the error is reported in the main loop, the parent does not proceed to Gate 1 in this run, and the user is told that the split was not applied.
- `apply` fails partway through → staging and rollback follow FTR-035 D-13. The main loop reports the failure and does not leave a partially created child set reported as complete.
- Retry after a failed `apply` → a fresh run that re-measures and proposes again with fresh IDs. The failed attempt is not resumed.

**Postconditions:**
- Accepted: the child features exist, registered per the FTR-035 contracts. The parent has stopped before Gate 1 and has no Gate 1 digest in this run. The parent's own documents are not changed by this use case.
- Rejected: the pipeline has reached Gate 1 with the parent's documents unchanged. No split, rejection, or proposal is stored.
- Unanswered or failed: nothing is stored, apart from anything `apply` itself completed under FTR-035 D-13 rollback rules.
- Open question: the staging, rollback and fresh-ID rules for partial failure and retry are defined in FTR-035 D-13 and in the Tech-Spec resolutions T-4 and T-5. They are referenced here rather than restated, because `feature.md` does not state them. The requirements owner should confirm that AC-20 and AC-21 cite these same rules.
