### UC-01: Measure feature size after Tech-Spec

| Field | Value |
|-------|-------|
| Actor | Pipeline (`pm-phase1`) |
| Preconditions | The Requirements and Tech-Spec documents have been generated and the `pm-phase1` validation loop has finished. The feature folder exists. The four thresholds (use cases, acceptance criteria, components, estimated phases) are available from the FTR-035 configuration keys. |
| Trigger | `pm-phase1` finishes the validation loop and reaches the point before the Gate 1 digest. |
| Priority | Must |

**Main flow:**
1. `pm-phase1` runs `check-size` through `run-asset scripts/feature-split.js --project <root> -- check-size --feature-dir <dir> --prefix <FTR-ID>`, using the `c.command` form already used in `pm-phase1.js`.
2. `check-size` applies the FTR-035 new-feature test to the feature folder. The folder is not new if it contains `{PREFIX}-Approvals.md`, a `wbs/` directory, or `epic.md`. A folder that does not exist yet is new. If the feature is not new, `check-size` returns `status: "skipped"` and the flow ends.
3. If the feature is new, `check-size` measures the four counts (feature.md D-01):
   - **Use cases:** the number of distinct `UC-NN` identifiers across `req/use-cases/*.md`.
   - **Acceptance criteria:** the number of distinct `AC-NN` identifiers in `req/index.md`.
   - **Components:** the number of rows of the component table in `spec/index.md`.
   - **Estimated phases:** the number of dependency levels of the Tech-Spec Section 11 build order, which is stored in `spec/index.md`. Each item is parsed as `N. <text> — depends on: <M[, M…]>` or `N. <text> — depends on: none`. The depth of an item is 0 when it has no dependencies, and otherwise one more than the greatest depth among its dependencies. The count is the greatest depth plus one.
4. `check-size` compares each count with its threshold using `isOverThreshold` (FTR-035 D-05). A count that is over its threshold is listed in `over`. A count equal to its threshold passes.
5. If any count is over its threshold and no count is unavailable, `check-size` returns `status: "split-proposed"` with a `proposal` in the FTR-035 D-08 shape with `source: "measured"`. The pipeline then stops before Gate 1 and the proposal is handled in UC-02.
6. If no count is over its threshold and no count is unavailable, `check-size` returns `status: "passed"` and the pipeline continues to the Gate 1 digest without a prompt.
7. `check-size` prints `{ status, counts, thresholds, over, unavailable, proposal }` with the key names of FTR-035 D-02.
8. `pm-phase1` adds the result to its return value as `split_checkpoint`, with the same shape.

**Alternative flows:**
- Feature is not new (the folder contains `{PREFIX}-Approvals.md`, a `wbs/` directory, or `epic.md`) → `status: "skipped"`, no measurement, no prompt, the pipeline continues to Gate 1.
- All four counts are at or below their thresholds → `status: "passed"`, no prompt, the pipeline continues to Gate 1 (BR-02).
- A count is exactly equal to its threshold → that count passes (D-03). It is not listed in `over`.
- One or more counts are over their thresholds, and every count is measurable → `status: "split-proposed"` and the pipeline stops before Gate 1 (handled in UC-02).

**Error flows:**
- A source file or table is missing or empty (`req/use-cases/*.md`, `req/index.md`, the component table in `spec/index.md`, or the Section 11 build order) → that count is unavailable, with the reason named. `status: "unavailable"` (exit 1). The report is a plain error in the main loop, not a gate or approval prompt (D-04).
- The Section 11 build order has a dangling dependency, a cycle, or an item with no `depends on:` clause → the estimated phases count is unavailable with the reason named (D-02).
- The `check-size` command fails, exits non-zero, or returns a missing or non-JSON result → `pm-phase1` reports the check as unavailable and does not parse the result unguarded (BR-04). The pipeline does not reach Gate 1 (BR-03).
- A count cannot be measured → it is reported as unavailable and never counts as passing. The check stops and the pipeline does not reach Gate 1 until the cause is fixed (BR-03).

**Postconditions:**
- `pm-phase1` returns `split_checkpoint` with exactly one of the statuses `skipped`, `passed`, `unavailable`, or `split-proposed`.
- On `skipped` or `passed`, the pipeline continues to the Gate 1 digest.
- On `unavailable`, the pipeline stops before Gate 1 and each unavailable count is reported with its reason.
- On `split-proposed`, the pipeline stops before Gate 1 and the proposal is passed to `implement-feature` for presentation (UC-02).
- Thresholds are the FTR-035 configuration values. The placeholder values are useCases 8, acceptanceCriteria 15, components 30, and estimatedPhases 6. These are placeholders, not confirmed values, until FTR-035 confirms them.
- Open question: `feature.md` does not state the `status` when one count is over its threshold and another count is unavailable. Only the unavailable count is reported under BR-03; the handling of the over count in that case is not specified.
