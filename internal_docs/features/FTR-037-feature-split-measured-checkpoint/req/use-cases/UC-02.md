### UC-02: Propose a split before Gate 1

| Field | Value |
|-------|-------|
| Actor | Pipeline; `implement-feature` main loop; User |
| Preconditions | Requirements and Tech-Spec are generated and the `pm-phase1` validation loop has completed, so UC-01 has measured the four counts. The feature is new under the FTR-035 new-feature test: its folder does not contain `{PREFIX}-Approvals.md`, a `wbs/` directory or `epic.md`, or the folder does not exist yet. At least one count is over its threshold. The thresholds are the FTR-035 configuration keys; their placeholder values are useCases 8, acceptanceCriteria 15, components 30 and estimatedPhases 6. |
| Trigger | `pm-phase1` returns `split_checkpoint` with `status: "split-proposed"`, and `implement-feature` Step 1a receives it between `pm-phase1` and Gate 1. |
| Priority | Must |

**Main flow:**
1. `implement-feature` Step 1a reads `split_checkpoint` from the `pm-phase1` return value. It is a `"split-proposed"` result, so the proposal is presented and no Gate 1 digest is shown yet.
2. Show each over-threshold count from `over` beside its threshold from `thresholds`, using the `counts` values (for example, "use cases: 9 (threshold 8)").
3. Present the proposal from `proposal` (FTR-035 D-08 shape, `source: "measured"`). For each child, show:
   1. its title and purpose;
   2. the use cases assigned to it, by `UC-NN` identifier and title;
   3. the components assigned to it, from the component table in `spec/index.md` (D-01);
   4. its Summary and Keywords. Keywords are derived by the agent from the child's title, use cases and components (D-09).
4. State the shared foundation (D-07). It is assigned to the first child in dependency order, which holds the components at depth 0 of the Tech-Spec Section 11 build order. If the build order has no distinct depth-0 level, the proposal states that no foundation is assigned.
5. Wait for the user's answer: accept, edit or reject. The user may edit only the following fields (restated from Tech-Spec Section 9 to be verifiable under AC-16; the FTR-035 D-09 to D-11 wording is not repeated here):
   - child names;
   - child purposes;
   - child order;
   - the foundation owner;
   - adding, removing or merging children;
   - Summary;
   - Keywords;
   - refusal of any edit that leaves fewer children than the FTR-035 `minChildren` value.
6. On accept, the `apply` call from FTR-035 runs in the main loop, not inside the workflow (D-06). The pipeline then stops for the parent. UC-03 covers apply in full.
7. On reject, the pipeline continues to Gate 1 unchanged and stores nothing (D-10).

**Alternative flows:**
- `status` is `"passed"` or `"skipped"` → no prompt is shown and the pipeline continues to Gate 1 (BR-02, D-11).
- User edits the proposal → the edit is applied to the proposal's editable fields (listed in step 5). Whether the edited proposal is shown again before accept is not specified in feature.md. See the open question below.
- No distinct depth-0 level in the build order → the proposal states that no foundation is assigned (D-07).
- User rejects → continue to Gate 1 unchanged (D-10).

**Error flows:**
- `status` is `"unavailable"` (exit 1) → show a plain error in the main loop naming each unavailable count and its reason (D-04). It is not a gate and not an approval prompt. No proposal is shown, and the pipeline does not reach Gate 1 until the cause is fixed (BR-03).
- `split_checkpoint` is missing, failed or not JSON → report the check as unavailable and stop; it is never treated as passing (BR-04).
- Build order item without a `depends on:` clause, a dangling dependency, or a cycle → `estimatedPhases` is unavailable with that reason (D-02).
- A source file or table is missing or empty → that count is unavailable (D-04).
- An edit that leaves fewer children than `minChildren` → refuse the edit and keep the proposal as it was before the edit.

**Postconditions:**
- After accept: the FTR-035 `apply` call runs and the pipeline stops for the parent (UC-03).
- After reject: Gate 1 is reached unchanged, and nothing is stored (D-10).
- After `passed` or `skipped`: Gate 1 is reached with no prompt (BR-02).
- After `unavailable`: Gate 1 is not reached, and no split is created or stored.
- Open question: feature.md D-09 says the agent derives Keywords, but does not say when that happens relative to `check-size` printing the proposal (D-05). It is not stated whether the proposal the user sees is the one `check-size` printed, or an agent-revised copy with Keywords added.
- Open question: feature.md D-08 names the parts given to each child (use cases and components) but does not define the rule that assigns them. Open gap 5 is still unresolved.
- Open question: feature.md D-07 needs components at depth 0 to identify the foundation, but does not define how a component maps to a build-order item. The foundation owner cannot be determined from feature.md alone.
- Open question: feature.md does not say whether an edited proposal is shown again for confirmation before accept runs.
