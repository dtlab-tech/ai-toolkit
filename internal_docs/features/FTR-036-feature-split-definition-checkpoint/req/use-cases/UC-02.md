### UC-02: Accept, edit or reject the split proposal

| Field | Value |
|-------|-------|
| Actor | User (via define-feature main loop) |
| Preconditions | UC-01 has run and returned `status` `"flagged"` for the feature. The proposal (child names, one-line purpose per child, dependency order, shared parts for the first child, the D-02 flow list with reasons, and editable Summary and Keywords per child) has been generated. Nothing has been written to disk. |
| Trigger | The proposal is presented to the user in the main loop, and the user replies with accept, edit or reject. |
| Priority | Must |

**Main flow:**
1. The `define-feature` agent returns the proposal to the main loop. It shows every item: child names, one-line purposes, dependency order, shared parts assigned to the first child, the flows with their reasons, and each child's Summary and Keywords as editable items (D-07).
2. The main loop asks the user to accept, edit or reject. The user's response is the only trigger for any write (BR-01, BR-03). Until then, nothing is written to disk.
3. The main loop re-invokes the agent with explicit state: the proposal, the user's decision and any edits. The grilling record is passed in that explicit state; it is not assumed to persist implicitly across the handoff, and it is never written to disk (D-03).
4. On accept, the agent first writes the parent `feature.md` and registers it with `register` (status defined). Only then does it run `apply --parent` from FTR-035 to create the children, because apply in initial mode requires a defined parent. This registration of the split parent is an explicit refinement of D-08, which by itself covers only a feature.md that is not split, and it cites the FTR-035 apply initial-mode precondition.
5. On edit, the user changes any item shown in step 1. Edits follow FTR-035 D-09 and D-10, including the foundation warning (D-06). The agent applies the edits and presents the revised proposal for accept or reject again. No write occurs until the user accepts.
6. On reject, the feature continues as a standalone feature (D-05). The agent writes its `feature.md`, and because it is not split, runs `register` (D-08). The Summary is the first sentence of the feature's Summary section. Keywords are derived from the title and main terms, shown to the user and editable.

**Alternative flows:**
- User accepts without edits → steps 4 proceed with the proposal as shown.
- User edits one or more items → the agent applies the edits, shows the revised proposal, and waits for accept or reject (step 5).
- User edits repeatedly → each revision is shown again; the loop ends only on accept or reject.
- User rejects after editing → the feature is treated as rejected, and the standalone path (step 6) applies. Edits made before the rejection are discarded.

**Error flows:**
- Target `feature.md` already exists at write time → the file is not overwritten (BR-04). Open question: `feature.md` does not specify the response when the target exists; the agent does not choose one for this UC.
- `apply --parent` fails partway → the agent reports which children were created, and offers retry, edit or reject. While a `.split-staging-*` leftover exists, later applies are blocked.
- Edit that alters the foundation child → the foundation warning from FTR-035 D-09 and D-10 is shown before the revised proposal can be accepted.

**Postconditions:**
- Accept: the parent `feature.md` is written and registered with status defined; the children created by `apply --parent` exist; the shared parts are assigned to the first child (D-09).
- Reject: the standalone `feature.md` is written and registered; the feature is treated as standalone, and checkpoint 2 (FTR-037) still runs for it later (D-05).
- Partial apply failure: the created children are reported; retry, edit or reject is offered; later applies are blocked while a `.split-staging-*` leftover exists.
- Before the user accepts or rejects: no file has been written and no registration has occurred (BR-01, BR-03).
