### UC-03: Create a late child of an existing epic

| Field | Value |
|-------|-------|
| Actor | User (via define-feature) |
| Preconditions | The features root resolves through `ai-toolkit resolve-features-root`. The user names an existing epic by its exact FTR-ID, and that epic's folder contains `epic.md`. The epic's registry status is `epic`, so it is neither in progress nor approved. |
| Trigger | The user asks `define-feature` to add a missing child to an existing epic. |
| Priority | Should |

**Main flow:**
1. The user asks `define-feature` for a missing child of an existing epic and names the epic's FTR-ID.
2. The agent resolves the features root with `ai-toolkit resolve-features-root`. It does not hard-code a path.
3. The agent looks for a folder whose name is an exact FTR-ID match for the named epic and that contains `epic.md`.
4. The agent reads the epic's registry status. It proceeds only if the status is `epic`.
5. The agent asks the user for the child's title and a one-line purpose.
6. No grilling round runs for the late child.
7. The agent derives the child's Summary and Keywords from its purpose and the epic's Summary, since no grilling answers exist for this path. It shows both to the user as editable items. This is an explicit refinement of D-07 for the late path.
8. The agent checks whether a `feature.md` already exists for the child it would create.
9. The agent presents the proposal: child title, purpose, Summary, Keywords, and the dependency on the epic's current last child. The child is placed last.
10. The user confirms. Nothing is created before confirmation (BR-01).
11. On confirmation, the agent runs the FTR-035 `apply` command to create the child, placed last, depending on the previous last child.
12. The agent does not call `register` for the child. The child belongs to the epic and is not a standalone feature.
13. The agent reports the created child's path and ID to the user.

**Alternative flows:**
- The user edits the proposed Summary or Keywords before confirming → the agent applies the edits per FTR-035 D-09 and D-10 (per D-06), including the foundation warning where it applies, then returns to step 9.
- The user rejects the proposal at step 10 → nothing is created and nothing is written. The child does not fall back to a standalone feature.

**Error flows:**
- `ai-toolkit resolve-features-root` fails → stop, report the failure to the user, and write nothing.
- No folder matches the named FTR-ID exactly, or the matching folder has no `epic.md` → list the candidate epics (folders containing `epic.md`) to the user and stop. Nothing is created.
- The epic's registry status is not `epic` (in progress or approved) → refuse, state the status as the reason, and stop. Nothing is created.
- The child's `feature.md` already exists → report that it exists and stop. The agent never overwrites it (BR-04).
- The FTR-035 `apply` command fails → report the failure to the user and write nothing further. The failure handling defined by FTR-035 `apply` applies.

**Postconditions:**
- On success, the child exists as the last child of the epic, depending on the previous last child, with the confirmed Summary and Keywords.
- On success, no `register` call is made for the child, and no standalone registration exists for it.
- On every refusal or rejection, no file is created or modified, and no standalone feature is created.
- No grilling round was run for the late child.
