### UC-01: Assess a new feature at definition time

| Field | Value |
|-------|-------|
| Actor | define-feature agent (with User) |
| Preconditions | The `define-feature` agent has completed Phase 3 (grilling) and holds the grilling answers in memory. `feature.md` has not yet been written for this feature (BR-04). The features root can be resolved with `ai-toolkit resolve-features-root` (D-10). The FTR-035 `feature-split.js` facade and its `check-definition` command are available. |
| Trigger | Phase 3 (grilling) finishes and the agent enters Phase 3a, before Phase 4 writes `feature.md`. |
| Priority | Must |

**Main flow:**
1. The agent builds the grilling record in memory as JSON: `{ "actors": [], "applications": [], "flows": [{ "name": "", "reason": "" }] }` (D-03). The record is never written to disk (BR-03, D-03).
2. The agent counts the independently deliverable flows itself (D-02). A flow is a user-visible capability that can be delivered on its own. Each flow is listed by name with a one-line reason. The visible list is the control; no counting algorithm is applied.
3. The agent resolves the features root by running `ai-toolkit resolve-features-root`. It does not hard-code a path (D-10).
4. The agent runs `run-asset scripts/feature-split.js --project <root> -- check-definition --features-root <path> --feature-id <FTR-ID>` and pipes the record on stdin (D-04).
5. The command prints `{ status, signals, flows, unevaluated }`:
   - `status` is `"skipped"`, `"not-flagged"` or `"flagged"`.
   - `signals` holds each count against its minimum.
   - `flows` is the list from step 2.
   - `unevaluated` names any signal that could not be evaluated from the grilling answers.
6. If `status` is `"skipped"`, the feature is not new and no check or proposal is shown. The agent continues to Phase 4 (see Alternative flows).
7. If `status` is `"not-flagged"`, nothing is proposed. The agent continues to Phase 4 and registers the feature as standalone (D-08). If `unevaluated` is non-empty, the agent names each signal it could not evaluate before continuing (BR-02).
8. If `status` is `"flagged"`, the agent proposes a split before writing anything (BR-01, BR-03). The proposal shows:
   - the child names;
   - a one-line purpose for each child;
   - the dependency order between children;
   - which shared parts belong to the first child;
   - each child's Summary and Keywords as editable items (D-07).
   The parts assigned to each child are the relevant grilling answers (D-09).
9. The agent hands the proposal to UC-02 for accept, edit or reject in the main loop. No file is written in this use case.

**Signal rule:** a feature is flagged as a probable epic if the grilling answers reach at least one of these minimums (D-01, FTR-035 D-05, Tech-Spec Section 8): `minActors` 2 actors, `minApplications` 2 applications, or `minFlows` 3 independently deliverable flows. A signal that cannot be evaluated does not count toward the flag (BR-02).

**Feature-not-new test:** the check is skipped when `isNewFeature` returns not-new, that is, when the feature already has an `epic.md`, a `{PREFIX}-Approvals.md`, or a `wbs/` directory present (Tech-Spec Section 12).

**Alternative flows:**
- Feature is not new (`status` = `"skipped"`) → no check and no proposal are shown; the agent continues to Phase 4 and writes `feature.md` as a non-split feature, registered per D-08.
- `status` = `"not-flagged"` with one or more `unevaluated` signals → nothing is proposed; the agent names each unevaluated signal to the user and continues to Phase 4 as standalone (BR-02).
- `status` = `"flagged"` and the user accepts the proposal → UC-02 applies the split. This use case ends at the proposal.
- `status` = `"flagged"` and the user edits or rejects the proposal → handled in UC-02. A rejected proposal continues as a standalone feature, and checkpoint 2 (FTR-037) still runs for it later (D-05).
- Flagged by flows alone (`minFlows` reached while actors and applications are below their minimums) → the same proposal is shown; the flagged reason is the flow list.

**Error flows:**
- `ai-toolkit resolve-features-root` fails → the agent stops, reports the failure to the user, and writes nothing (Tech-Spec Section 6).
- `check-definition` receives an unparseable grilling record (`RECORD_INVALID`) → the agent stops, reports the error, and writes nothing (Tech-Spec Section 6).
- A signal cannot be evaluated from the grilling answers → it is not counted toward the flag, and the agent names it to the user (BR-02). This is not a stop condition.

**Postconditions:**
- `status` = `"skipped"` or `"not-flagged"`: the agent writes `feature.md` as a non-split feature in Phase 4 and runs `register` for it as standalone (D-08, FTR-035 D-25). The Summary is the first sentence of the feature's Summary section. The Keywords are derived from the title and main terms, shown to the user, and editable by the user.
- `status` = `"flagged"`: the proposal is presented to the user and no file has been written (BR-01, BR-03). The split decision is passed to UC-02.
- Error flows: nothing is written to disk and no `register` call is made.
- The grilling record exists only in memory and is not persisted at any point (D-03).
- If `feature.md` already exists for this feature, it is not overwritten (BR-04).
