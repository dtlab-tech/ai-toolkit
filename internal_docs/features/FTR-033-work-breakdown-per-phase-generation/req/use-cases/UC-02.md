### UC-02: Generate One Phase's Own Tasks Per Call

| Field | Value |
|---|---|
| Actor | `gaia-generate-work-breakdown-phase` (new) / `pm-phase2` coordinator |
| Priority | Must |
| Preconditions | UC-01's phase-enumeration call has returned the ordered phase list |
| Trigger | `pm-phase2.js` dispatches one call per phase, in enumerated order |

> **Legend:** **Actor** — who/what initiates or participates in this use case. **Priority** —
> MoSCoW (Must/Should/Could). **Preconditions** — what must already be true before this use case
> can start. **Trigger** — the event that starts it.

This is the direct replacement for the real failure: deciding one phase's own tasks (structural
fields only — title/outcome/domain/agentType/dependsOn/acceptanceCriteria/outputCount/commit, same
as today's per-task skeleton entry) is a MUCH smaller, bounded generation than deciding the whole
feature's task graph at once, and completes reliably at the scale a real 10-UC feature actually
needs.

1. **New agent: `gaia-generate-work-breakdown-phase`.** Dispatched once per phase, strictly in the
   order UC-01 enumerated (INFRA first, if present, then US phases in priority order) — never
   concurrently, never out of order.
2. **Scoped Requirements input.** Only the UC(s) this phase's own `sourceUC` realizes — not the
   full Requirements text already inlined at UC-01's own phase-enumeration tier. The per-task
   DETAIL pass (UC-03) already establishes the precedent that a later, more specific generation
   step gets a NARROWER slice of Requirements/Tech-Spec than the index-level call before it; this
   UC applies the same narrowing one tier earlier.
3. **Scoped Tech-Spec input.** The Tech-Spec skeleton (Section 9's component index, same as
   today), plus the SAME bounded `needsComponentDetail` drill-down FTR-032 already built — a
   phase's own call may request specific components' own design bodies if genuinely needed,
   exactly as the whole-feature call already could; the host answers with a single, bounded second
   call, unchanged mechanism.
4. **Prior-phase task visibility — lightweight projection only.** Every task already decided by a
   PRIOR phase is given as `id`/`title`/`outcome`/`domain` (not the full task object) — enough to
   reference a real prerequisite in `dependsOn` and to recognize/avoid re-implementing something
   already built, without the prompt growing by a full task object's worth of text per task as
   prior phases accumulate (Open Question 1, resolved: lightweight projection, mirroring
   `buildTaskPrompt`'s own existing "siblings" list for the per-task DETAIL pass).
5. **Never a later phase's tasks.** A phase being generated now has no way to know, and must never
   be told to reference, a phase that has not been enumerated-and-generated yet — this is a
   structural property of sequential, in-order generation, not an extra check this UC adds.
6. **Phase `context` is produced here, not at UC-01.** Now that this phase's own tasks are fully
   known, write the 2-4 sentence narrative context exactly as today's single-call generator already
   does — this is the one field UC-01 deliberately deferred.
7. **Incremental persistence.** Immediately after a phase's own call returns (and, if it fired,
   its drill-down round completes), that phase's tasks are written to `index.json` before the NEXT
   phase's call is ever dispatched — a crash or failure on phase N+1 never loses phase N's already
   -persisted work.
8. **Resume.** A re-run checks `index.json` for the first phase without a `taskIds` entry yet and
   resumes there — every already-completed phase is skipped, never redispatched.
