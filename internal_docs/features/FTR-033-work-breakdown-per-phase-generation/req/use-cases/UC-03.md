### UC-03: Per-Task Detail Generation Is Unaffected

| Field | Value |
|---|---|
| Actor | `gaia-generate-work-breakdown-task` (existing, FTR-020) |
| Priority | Must |
| Preconditions | UC-01 and UC-02 have together produced the complete skeleton (every phase, every task) |
| Trigger | `pm-phase2.js`'s existing per-task detail loop runs, unchanged |

> **Legend:** **Actor** — who/what initiates or participates in this use case. **Priority** —
> MoSCoW (Must/Should/Could). **Preconditions** — what must already be true before this use case
> can start. **Trigger** — the event that starts it.

This UC exists only to state, explicitly and testably, what does NOT change: the existing per-task
DETAIL generation pass reads `index.json`'s own fully-assembled `tasks` map exactly as it does
today — it has no way to tell, and no reason to care, whether that map was produced by one
monolithic call (the old behavior) or by a phase-enumeration call plus N per-phase calls (this
feature's own new behavior). `index.json`'s own on-disk shape (`schemaVersion: 3`, every phase/task
field) is byte-for-byte identical either way.

1. **No code change required for this pass itself** — included as a UC specifically so the
   Work Breakdown and test suite can assert this explicitly (AC-07), not just assume it.
2. **Resume-by-status is unaffected.** The existing `task.status === 'generated'` + detail-file
   validity check (FTR-027) that lets a resumed run skip an already-generated task's own detail
   file works identically regardless of how the surrounding skeleton came to exist.
