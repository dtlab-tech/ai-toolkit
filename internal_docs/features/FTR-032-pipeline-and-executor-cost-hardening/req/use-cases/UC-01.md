### UC-01: Shrink the WBS Skeleton Call to Index-Row Weight

| Field | Value |
|---|---|
| Actor | `pm-phase2` coordinator |
| Priority | Must |
| Preconditions | A feature's Work Breakdown skeleton has not yet been generated (or is being regenerated from scratch) |
| Trigger | `pm-phase2.js` dispatches its `gaia.agent.planner.work-breakdown` skeleton call |

> **Legend:** **Actor** — who/what initiates or participates in this use case. **Priority** —
> MoSCoW (Must/Should/Could). **Preconditions** — what must already be true before this use case
> can start. **Trigger** — the event that starts it.

Confirmed by direct code inspection that Requirements, Tech-Spec, and Work Breakdown skeleton
generation all share the identical SHAPE — one single skeleton call, then N per-item detail calls
— so "WBS is monolithic, req/spec are per-item" is not an accurate framing of the asymmetry. The
real difference is payload WEIGHT: Requirements/Tech-Spec skeleton calls need only lightweight
index-row fields per item (ID, title, a one-line summary); the WBS skeleton call's own
`SKELETON_SCHEMA` requires, for EVERY task across the WHOLE feature in one turn: title, outcome,
domain, agentType, dependsOn, acceptanceCriteria, an effort estimate (agentMinutes + tokens),
outputCount, and a commit type/subject. Of these, the effort estimate is qualitatively different —
producing a genuinely useful per-task agentMinutes/tokens number requires the model to implicitly
reason through how it would implement that task, not merely classify or summarize it, unlike every
other field in the list. Reported against a real feature (`Fincantieri.CommonLibraries.MFExample`
FTR-003 — 13 ACs, 10 UCs, ~49-58 Tech-Spec components, plausibly many tasks): 6/6 consecutive
attempts across two separate invocations failed identically with
`"API Error: Stream idle timeout - no chunks received"` on this exact dispatch.

A second, decisive finding from direct code inspection: the per-task DETAIL call
(`gaia.agent.planner.work-breakdown-task`) ALREADY asks the model to produce a real `estimate` in
every single call — its own template (`gaia-task-template.md`) includes "Estimate — agent
minutes"/"Estimate — tokens" as two of its 14 required field placeholders. Today the host silently
DISCARDS that value: `wbs-assembler.js`'s `parseTaskDetailBlock` only ever reads back
`groupingRationale` and verification commands from a task detail response; `loadWorkBreakdown`'s
per-task mapping takes `estimate` from the SKELETON-derived data instead. This means fixing UC-01
requires no new prompt text and no new field the model must produce anywhere — it only requires
changing WHICH of the two already-produced copies the host trusts.

1. **Remove `estimate` from `SKELETON_SCHEMA`.** The skeleton call's per-task `required`/
   `properties` no longer include `estimate` — `materializeIndex` no longer copies it into
   `index.tasks[taskId]`.
2. **Read `estimate` back from the per-task detail response instead.** `wbs-assembler.js`'s
   `parseTaskDetailBlock` gains `estimate: {agentMinutes, tokens}` to its returned object, parsed
   from the SAME contiguous field block it already reads `groupingRationale` from (no new parsing
   logic category — the two fields are already present in that block, just not yet extracted).
3. **`loadWorkBreakdown`'s per-task mapping switches its source.** Where it previously set
   `estimate: skeletonTask.estimate`, it now sets `estimate: detail.estimate` — propagating to
   every consumer of the assembled structure (`wb-render.js`, `wb-validate.js`, `ac-task-matrix.js`,
   and the task executor's own `_loadPlanDocs` fallback, FTR-030) uniformly, with no separate change
   needed in any of them.
4. **Every other skeleton-level field is unchanged.** Title, outcome, domain, agentType,
   dependsOn, acceptanceCriteria, outputCount, and commit stay in the skeleton — each is either
   genuinely cheap (a short string, an enum, an ID list) or gates a real structural check that runs
   BEFORE any per-task dispatch (`wb-skeleton-check.js`/`wb-graph-checks.js`'s DAG and AC-coverage
   checks need `dependsOn`/`acceptanceCriteria` at skeleton time; neither reads `estimate`).
5. **`c.estimates()`'s own consumption is unaffected.** It already runs AFTER every per-task detail
   call completes, per `pm-phase2.js`'s existing flow (`const assembled = ...; const metrics =
   await c.estimates(...)` happens once, at the very end); `wb-validate.js`'s own duration-band
   checks (check 15) already operate on the assembled structure too, per that file's own comment
   that it "needs per-task estimate detail, not just the skeleton shape `wb-graph-checks.js` works
   with" — confirming neither downstream consumer's timing changes.
6. **A resumed run from a pre-fix skeleton (estimate already present in an on-disk `index.json`)
   is read as-is** — this UC only changes what a NEW skeleton generation call asks for and which
   source a NEW assembly read trusts; an existing on-disk `index.json`'s own `estimate` field, if
   present from a prior toolkit version, is simply ignored by the new `loadWorkBreakdown` mapping
   in favor of the per-task detail file's value (already present and correct in that case too,
   since the per-task call always wrote a real estimate, even when it went unused).
