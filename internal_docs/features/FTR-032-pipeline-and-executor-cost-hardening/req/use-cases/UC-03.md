### UC-03: Short-Circuit Dispatch for an Already-Satisfied Task

| Field | Value |
|---|---|
| Actor | `_runTaskToResolution` (`lib/task-executor/index.js`) |
| Priority | Must |
| Preconditions | A task is about to begin its FIRST attempt (not a retry); the task declares one or more verification commands |
| Trigger | `_runTaskToResolution` is entered for a task whose attempt count is currently zero |

> **Legend:** **Actor** — who/what initiates or participates in this use case. **Priority** —
> MoSCoW (Must/Should/Could). **Preconditions** — what must already be true before this use case
> can start. **Trigger** — the event that starts it.

Reported against the same real run as UC-02: `INFRA-TASK-DB-01`'s own verification commands (one
small `dotnet build` plus two `grep` checks) measured directly at ~5-10 seconds combined — yet the
executor still paid for a full ~15-minute implementation dispatch and a full ~5-minute review
dispatch before its EXISTING no-op-checkpoint logic recognized there was nothing to stage. That
existing `'skipped'` path (added for a different, already-fixed bug: a deliverable already
committed by a prior attempt or a prerequisite task) is only ever reached AFTER both dispatches
already succeeded — there is no cheaper pre-check today.

1. **Run verification once, before any dispatch, on a task's first attempt only.** If the task
   declares one or more verification commands, they are run against the current project directory
   exactly as the existing `runVerifications` already does post-dispatch — but BEFORE
   `dispatchTaskAttempt` is ever called for that attempt.
2. **All-pass means already satisfied.** If every verification command already passes, the task is
   marked `'skipped'` directly — the SAME terminal status/meaning the existing post-hoc path
   already uses — WITHOUT dispatching the implementation agent or the review agent for that
   attempt at all.
3. **Any failure means proceed normally.** If at least one verification command fails (or there
   are none at all), the short-circuit does not apply — a normal implementation dispatch proceeds,
   unchanged from today.
4. **Never applies to a retry.** The short-circuit only runs before a task's FIRST attempt. A
   second or later attempt (a retry after a prior failure) always proceeds to a normal dispatch —
   a prior failed attempt already proves verification did not already pass at task start, and this
   UC makes no claim about whether it might pass again by coincidence mid-retry.
5. **A genuine verification-tooling failure propagates unmodified** — exactly as a post-dispatch
   verification failure would today; this UC never silently treats a broken check as "proceed with
   dispatch anyway."
