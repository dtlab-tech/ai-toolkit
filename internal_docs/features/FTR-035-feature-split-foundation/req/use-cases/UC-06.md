### UC-06: Generator agents read registry entries and epic records

| Field | Value |
|-------|-------|
| Actor | Requirements and Tech-Spec generator agents |
| Preconditions | The feature folder for the feature being generated exists under the features root. The feature registry `REGISTRY.md` (path resolved with `ai-toolkit resolve-features-root`) exists and is readable. Child and epic entries use the registry layout of D-18: `Status`, `Keywords`, `Summary`, and the bold-key lines `Parent:` and `Depends on:`. |
| Trigger | A Requirements or Tech-Spec generation run starts for a feature ID. |

**Main flow:**
1. The generator resolves the features root with `ai-toolkit resolve-features-root` and reads `REGISTRY.md`.
2. The generator finds the entry for the feature's own ID and reads its `Status`, `Keywords`, `Summary`, and the optional `Parent:` and `Depends on:` lines.
3. If the entry has neither a `Parent:` line nor a `Depends on:` line, the generator treats the feature as standalone: no parent epic, no siblings, no dependency position. Generation then proceeds as it did before the registry lines existed.
4. If the entry has a `Parent:` line, the generator treats the feature as a child of the epic named there. It records the epic ID and reads `Depends on:`, which is either a list of sibling IDs or `none` for the first child in dependency order.
5. For a child, the generator reads the `epic.md` in the parent folder and takes from its split table the children, their order, their dependencies, the shared-foundation owner, and the checkpoint (`definition`, `measured` or `late`) that produced each child.
6. If the entry has `Status` `epic`, the generator recognises it as the epic record. The epic is not generated as a pipeline feature (BR-05). The generator reads its `epic.md`.
7. If the entry has any other `Status`, the generator leaves the entry untouched and does not treat it as an epic.
8. The generator writes nothing to `REGISTRY.md` or `epic.md`. Its handling of these files is read-only.

**Alternative flows:**
- Entry has no `Parent:` and no `Depends on:` line → standalone feature (main flow step 3).
- Child entry with `Depends on: none` → first child in dependency order. Per BR-03 this child carries the shared foundation.
- Child entry with `Depends on:` listing sibling IDs → those siblings are recorded as the feature's dependencies, in the order given.
- Epic entry (`Status` `epic`) → recognised as the epic record. Its `Keywords` are the union of its children's Keywords (D-19), and the generator reads them as ordinary keywords.
- Entry with a `Status` other than `defined`, `completed` or `epic` → left untouched and not treated as an epic (D-18). Whether the feature itself is still generated is not stated in feature.md.

**Error flows:**
- The feature ID has no entry in `REGISTRY.md` → not specified in feature.md. See the open question in Postconditions.
- The entry has a `Parent:` line but no `Depends on:` line → not specified in feature.md. See the open question in Postconditions.
- The entry has `Status` `epic` but the folder holds no `epic.md` → not specified in feature.md. See the open question in Postconditions.
- `REGISTRY.md` cannot be read → not specified in feature.md. See the open question in Postconditions.

**Postconditions:**
- The generator has classified the feature as standalone, child (with epic ID, dependency position and sibling dependencies), or epic record, based on its registry entry.
- For a child, the generator has read the epic's split table from `epic.md`.
- No registry or epic record was modified by the generator.
- Entries with an unrecognised `Status` are unchanged and not treated as epics.
- Open question: feature.md does not specify the generator's behaviour when (a) the feature ID has no registry entry, (b) an entry has `Parent:` but no `Depends on:` line, (c) an entry has `Status` `epic` but no `epic.md` exists in the folder, or (d) `REGISTRY.md` cannot be read. These cases need a decision at Gate 1.
