### UC-04: Apply a confirmed split (initial split or late child)

| Field | Value |
|-------|-------|
| Actor | Calling feature script; User (confirms) |
| Preconditions | **Initial split:** the parent folder under the features root (resolved by `ai-toolkit resolve-features-root`) holds the parent's `feature.md` and no `epic.md`, and the user has confirmed the proposal (BR-01). **Late child:** the parent folder holds `epic.md` and no `feature.md`, and the user has confirmed a proposal for one missing child of that epic (D-16). In both modes the configuration has been loaded (UC-01) and the proposal is in the D-08 shape. |
| Trigger | The user confirms a proposal, and the calling script runs `feature-split.js apply --features-root <root> --parent <FTR-ID>` with the confirmed proposal JSON on stdin. |
| Priority | Must |

**Main flow (initial split):**
1. Read the proposal JSON from stdin and validate its shape against D-08: `source` is `definition` or `measured`, `children` is a non-empty array, each child has `name`, `purpose`, `summary`, `keywords`, `dependsOn` and `assigned`, `sharedFoundationOwner` is a child name or null, and `minChildren` is present.
2. Determine the mode from the parent folder. If `epic.md` is present, go to alternative flow A1 (late child). If only `feature.md` is present, continue as an initial split. If neither is present, stop with error E1. Read the original `feature.md` text now, because it is kept verbatim in `epic.md`.
3. Validate each child name (non-empty, valid folder slug, no two children with the same slug, D-12). Validate that every `dependsOn` entry names a sibling child, that no child depends on itself, and that the dependencies form no cycle. Any failure is error E2.
4. Check that the number of children is at least `minChildren` (D-09). If it is not, stop with error E4.
5. Compute the dependency order: a topological order of the children from `dependsOn`, with ties broken by the order of children in the proposal. Check the shared foundation against BR-03. If `sharedFoundationOwner` is not the first child in this order, or is null, do not refuse. Record a warning that names the BR-03 break and its consequence (D-10), and carry it into step 7 (alternative flow A2).
6. Assign new IDs (BR-02). Take the next free `FTR-NNN` from the union of IDs in the registry and the folder names under the features root. Assign them in dependency order, so each child receives a distinct ID that is neither the parent's ID nor a suffixed form of it. If a computed ID already exists as a folder or a registry entry, stop with error E6.
7. Stage the run. Create `.split-staging-<run id>` directly under the features root. In it, write:
   - one folder per child, named `<ID>-<slug>` (matching the existing `FTR-NNN-slug` folder convention), each containing a `feature.md` with the title, summary (the purpose line), parent ID, dependency position, sibling dependencies (`none` for the first child), assigned parts, and the shared-foundation content (D-15; foundation content goes to the first child in dependency order);
   - a new `epic.md` with the split table (child ID and name, order, dependencies, shared foundation and its warning if one was recorded, and checkpoint, which is `source` for every child of an initial split) and the verbatim original feature text as a trailing section (D-14);
   - a restore copy of the original `feature.md`, used only for rollback.
8. Move into place with single same-volume renames:
   - (a) rename each staged child folder into the features root;
   - (b) rename the staged `epic.md` over the parent's `feature.md`. This replaces the original file, so the parent folder then holds only `epic.md` (D-14).
9. Registry (D-21, written last). Read `internal_docs/features/REGISTRY.md` (resolved via `resolve-features-root`, D-22), creating it if it is missing. Build the new content in memory, then write it through a temp file and a rename:
   - add one entry per child with the existing format (heading, Keywords, `Status: defined`, Summary as the purpose line, `Parent:` set to the epic ID, `Depends on:` set to the sibling IDs or `none`, and `Detail` linking to the child's `feature.md`);
   - change the parent's existing entry in place to `Status: epic`, with Summary set to the first sentence of the original Summary, Keywords set to the union of the children's Keywords, and `Detail` linking to the parent folder's `epic.md`. The epic entry is never duplicated;
   - add an entry only for an ID that is not already present, so a re-run does not duplicate entries.
   If the registry cannot be read or written, stop with error E8.
10. Clean up. Remove `.split-staging-<run id>` and everything in it, including the restore copy.
11. Print `{ "epic": "<parent ID>", "children": [{ "id": "<ID>", "dir": "<path>" }, ...], "registry": true }` and exit 0.

**Alternative flows:**
- A1 (late child): the parent folder holds `epic.md`. Apply uses the late mode instead of the initial-split steps:
  - the proposal must contain exactly one child (otherwise error E3);
  - `minChildren` does not apply to a late child, and `source` is ignored;
  - the child's checkpoint in `epic.md` is `late` (D-16);
  - its `dependsOn` defines its position. Every name must be an existing child of the epic, read from the split table in `epic.md`. If `dependsOn` is empty, the child is placed last and depends on the previous last child;
  - step 7 stages only the new child folder and an updated `epic.md`, which appends a row for the new child and keeps the existing rows and foundation row unchanged. The old `epic.md` is kept as the restore copy;
  - step 8 moves the new child folder into place and renames the updated `epic.md` over the old one. There is no `feature.md` step;
  - step 9 adds one child entry, recomputes the epic entry's Keywords as the union over all children (reading the prior children's Keywords from their entries), and leaves the epic Summary as it is.
- A2 (shared foundation broken, BR-03): the run proceeds and does not refuse. The warning is recorded in the shared-foundation row of `epic.md` and returned to the calling caller of the library function (D-10).

**Error flows:**
- E1: stdin is not valid JSON, the D-08 shape is violated, or the parent folder holds neither `feature.md` nor `epic.md` → `FeatureSplitError`; nothing is written.
- E2: a child name is empty, not a valid slug, or duplicates another slug; a `dependsOn` entry names an unknown sibling; or the dependencies form a cycle → rejected with a message naming the child; nothing is written.
- E3: a late-child run (`epic.md` present) with more than one child in the proposal, or with a child ID that already exists → rejected; nothing is written.
- E4: an initial split with fewer children than `minChildren` → refused (D-09); nothing is written.
- E5: the shared foundation is not on the first child → not an error; handled by A2.
- E6: a computed child ID already exists as a folder or registry entry → `FeatureSplitError`; the existing item is never overwritten; anything already staged is removed.
- E7: a staging, rename or write failure during steps 7–8 → roll back everything moved into place: remove the child folders, restore the original `feature.md` (or the old `epic.md` in late mode) from the restore copy, and remove the staging directory. Report the error. If the rollback itself fails, the run ends in error and lists the exact paths that remain.
- E8: the registry cannot be read or written in step 9 → remove everything moved into place (as in E7), register nothing, remove any temp file, and report the error (D-21).
- E9: `resolve-features-root` fails → error; nothing is written.

**Postconditions:**
- Initial split: the parent folder holds only `epic.md`, which contains the split table (with the checkpoint `source` for each child) and the verbatim original text. Each child folder under the features root holds a `feature.md` (D-15). The registry has the parent entry set to `epic` and one `defined` entry per child with `Parent:` and `Depends on:`. No `.split-staging-*` directory from this run remains.
- Late child: one new child folder holds its `feature.md`. `epic.md` has the new row with checkpoint `late` and the existing rows are unchanged. The registry has one new entry with `Parent:` and `Depends on:`, and the epic entry's Keywords are updated. No `.split-staging-*` directory from this run remains.
- No child is registered before `epic.md` exists.
- Open question: `feature.md` does not say what apply does when the registry has no entry for the parent ID (step 9). It could refuse, create the epic entry, or warn. This is not decided.
- Open question: `feature.md` does not say whether generated `req/` and `spec/` folders in the parent folder are moved, removed or kept at an initial split, given that D-14 says the parent folder holds only `epic.md`. This is deferred to Gate 1.
