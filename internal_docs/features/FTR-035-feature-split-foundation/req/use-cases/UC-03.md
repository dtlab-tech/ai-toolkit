### UC-03: Build and edit a proposal

| Field | Value |
|-------|-------|
| Actor | Calling feature script; User |
| Preconditions | The configuration has been loaded through UC-01, so `minChildren` is available. The caller has supplied at least one child with a name, purpose, keywords, `dependsOn` and `assigned` content. No file is required to exist, because a proposal is an in-memory object until UC-04 applies it. |
| Trigger | A caller invokes `buildProposal` with its children, or the user asks to edit a proposal that has been built and not yet confirmed. |
| Priority | Must |

**Main flow:**
1. The caller invokes `buildProposal` with `source` (`"definition"` or `"measured"`) and the list of children. Each child carries `name`, `purpose`, `keywords`, `dependsOn`, and `assigned`.
2. The module validates each child name (D-12). A name must be a non-empty string that yields a valid folder slug. Two children may not produce the same slug. A name that fails either check is rejected with a message that names the child, and the proposal is not built.
3. The module sets each child's `summary` to its one-line `purpose` (D-11). Keywords are kept as supplied by the caller.
4. The module counts the children. If the count is below `minChildren` from the configuration, the proposal is refused.
5. Dependency order is taken from the `dependsOn` lists. Where several children have an empty `dependsOn`, the order between them is their order in the proposal list (proposal order). The first child in dependency order is the one that has no sibling dependency and comes first in proposal order.
6. `sharedFoundationOwner` is set by default to the first child in dependency order (BR-03). `foundationNote` is set by the caller or left empty.
7. The module returns the proposal in the D-08 shape: `{ source, children, sharedFoundationOwner, foundationNote, minChildren }`.
8. The user reviews the proposal and may request edits. The module applies `editProposal` to each requested change: rename a child, change a purpose, change order, change the shared-foundation assignment, add a child, remove a child, or merge two children (D-09).
9. After each edit, the module re-validates names (step 2) and re-checks the count against `minChildren` (step 4). An edit that would leave fewer children than `minChildren` is refused, and the proposal stays as it was before the edit.
10. If the edit moves `sharedFoundationOwner` away from the first child in dependency order, the module returns a warning that BR-03 is broken and states the consequence: every later child depends on the shared foundation, and the first child is the one that must hold it. The edit is applied anyway (D-10).
11. The edited proposal is returned to the caller. It is not re-measured (D-09). It waits for the user's confirmation, which UC-04 requires before anything is applied (BR-01).

**Alternative flows:**
- The user edits only names or purposes → the proposal is returned with the new values, and no warning is produced.
- The user moves the shared foundation to the first child in dependency order → no warning is produced.
- The user adds a child → the child is validated under step 2 and placed in the order the user gives. The count check in step 9 applies.
- The user removes or merges children and the count stays at or above `minChildren` → the edit is applied, and the remaining children keep their order.
- The user makes no edit and confirms the proposal → the proposal is passed to UC-04 unchanged.

**Error flows:**
- Child name is empty or not a string → the name is rejected with a message, and the proposal is not built or the edit is not applied.
- Child name does not yield a valid folder slug → the name is rejected with a message that names the child.
- Two children yield the same slug → the duplicate is rejected with a message, and the proposal is not built or the edit is not applied.
- Child count is below `minChildren` at build time or after an edit → the proposal or edit is refused, and the previous proposal is kept.
- `minChildren` is missing or invalid because the configuration could not be loaded → the error from UC-01 (`FeatureSplitError`) is passed up, and the caller stops.
- Shared foundation moved away from the first child in dependency order → not an error. A warning is returned and the edit is applied (D-10).

**Postconditions:**
- A proposal in the D-08 shape exists in memory and is returned to the caller.
- Every child has a valid, unique slug and a summary equal to its purpose line.
- The child count is at least `minChildren`.
- `sharedFoundationOwner` is set, or is null if the caller left it unset.
- If the shared foundation was moved away from the first child, the warning has been returned to the caller.
- No file has been written. Writing happens only in UC-04, after the user confirms.
- Open question: `feature.md` does not say how a merged child combines the purposes and keywords of the two children it replaces.
- Open question: `feature.md` does not say whether `dependsOn` is rewritten when the user reorders children, or whether it is rejected if it names a child that no longer exists.
- Open question: `feature.md` does not say whether a `dependsOn` cycle is refused at build or edit time.
