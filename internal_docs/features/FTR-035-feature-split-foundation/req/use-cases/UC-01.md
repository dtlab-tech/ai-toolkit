### UC-01: Load configuration

| Field | Value |
|-------|-------|
| Actor | Calling feature script |
| Preconditions | The toolkit default `feature-split.config.json` exists in the `scripts` source directory (`src/claude/scripts/`). The caller knows the project root, where an optional project override may sit. |
| Trigger | A caller requests the configuration: `loadConfig` from the library, or any `feature-split.js` command that needs thresholds (`apply`, `register`, `check-definition`, `check-size`). |
| Priority | Must |

**Main flow:**
1. The caller asks the loader for the configuration.
2. The loader reads the toolkit default `feature-split.config.json` from the `scripts` source directory. If it is missing or unreadable, it stops with a `FeatureSplitError` (see error flow E1).
3. The loader checks for a project override `feature-split.config.json` at the project root. If none exists, it continues with the default alone (see alternative flow A1).
4. If the override exists, the loader reads it and overlays it on the default key by key. Each leaf key in the D-02 shape (`thresholds.useCases`, `thresholds.acceptanceCriteria`, `thresholds.components`, `thresholds.estimatedPhases`, `definitionSignals.minActors`, `definitionSignals.minApplications`, `definitionSignals.minFlows`, `minChildren`) that the override sets replaces the default value. Keys the override omits keep the default value (see alternative flow A2).
5. The loader validates every resulting value. Each must be an integer, not negative, and each key must belong to the D-02 shape. A violation is a loader error that names the key and the file, and the caller stops (see error flows E2 and E3).
6. The loader returns the merged configuration with the full D-02 shape, including `minChildren`. The caller uses these values as given and does not restate them (BR-04).

**Alternative flows:**
- A1: Project override file absent at the project root → the default alone is validated and returned. Absence is not an error.
- A2: Override contains a subset of keys (including an empty object `{}`) → the omitted keys keep their toolkit default values, and the returned configuration is complete.
- A3: Override sets a value of `0` → accepted as a non-negative integer and used as given. Feature.md does not state any further meaning for `0`, and this flow does not add one.

**Error flows:**
- E1: Toolkit default missing or unreadable → `FeatureSplitError` with `code` and `file` set (file: the default path); the caller stops and nothing is returned.
- E2: A value is not an integer or is negative (in the default or in the override) → `FeatureSplitError` naming the key and the file; the caller stops.
- E3: A key is not in the D-02 shape (in the default or in the override) → `FeatureSplitError` naming the key and the file; the caller stops.
- E4: Project override exists but cannot be parsed as JSON, or cannot be read → not decided by feature.md (see the open questions below). Until decided, the loader must not silently fall back to the default.

**Postconditions:**
- The returned configuration contains every D-02 key with an integer, non-negative value.
- The loader writes no file.
- Callers obtain thresholds only from this function, never from hard-coded values (BR-04).
- Open question: feature.md (D-03, D-04) does not classify a malformed or unreadable project override (E4). It only covers an unreadable toolkit default (E1) and invalid values (E2, E3). It is not stated whether a malformed override is an error that stops the caller or a warning that falls back to the default.
- Open question: feature.md (D-23) passes the project root to the facade through `--project`, but does not state how the library function `loadConfig` receives the project root. The parameter form is not specified.
- Open question: feature.md does not say what the `key` field of `FeatureSplitError` holds for file-level errors (E1), where no single key is involved.
