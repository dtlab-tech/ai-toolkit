# FTR-020 — Coverage Matrix (worked example)

> Manual, exploratory example of the "coverage table" discussed as the missing piece of Gate
> 1/Gate 2 validation — produced to decide the real shape before any code (`req-validate.js` or
> equivalent) gets written. Not itself a gate artifact yet; see "Open questions" at the bottom.

This pivots the AC-centric cross-references already declared elsewhere (`req/index.md`'s AC
table, each `spec/components/*.md`'s `Addresses:` field, each `wbs/index.json` phase's
`sourceUC`) into one AC-per-row view, so "is this AC covered end-to-end" is answerable without
opening four documents by hand. Data lives in [`matrix.json`](matrix.json).

## Generation model — `matrix.json` is a generated output, never hand-maintained

`matrix.json` **duplicates** facts that are already authoritative elsewhere (`criterion`,
`priority`, `relatedUC` from `req/index.md`; `specComponents` from each component's own
`Addresses:` field). Hand-maintaining that duplication would be a real drift risk — nothing would
catch `matrix.json` going stale after a `req/`/`spec/`/`wbs/` edit. The resolution, decided after
cross-checking this exact file against its sources and finding it *currently* consistent only
because it was just hand-built: **`matrix.json` must be a generated artifact, exactly like
`{PREFIX}-Work-Breakdown.md`/`.csv` are generated by `wb-render.js` and never hand-edited.** A
future `coverage-check.js` (or equivalent) reads `req/`, `spec/`, and `wbs/index.json`, computes
every field below, and **writes** `matrix.json` — failing (blocking the gate) if any Must AC
comes back `gate1Covered: false` or `gate2Covered: false`. Under this model the duplication above
stops being a liability: a generated file can restate source data freely, the same way
`wb-render.js`'s rendered `.md` already restates everything from the validated JSON — it can
never drift because it's recomputed, not edited.

This runs as part of the existing gates, not a new one — mirroring `wb-validate.js`'s placement
inside `pm-phase2.js` today: inside **Gate 1** (once `req/`+`spec/` exist, before human
approval) and inside **Gate 2** (once the Work Breakdown exists, before human approval).

**Today**, no such generator exists — this file was hand-authored as a worked example, then
verified with a throwaway script that recomputed every field from the real sources and diffed
against it (found zero mismatches, after that same process had already caught and fixed a real
error — see Finding 1 below). In this exploratory stage, re-running that same throwaway check by
hand after any edit to `req/`, `spec/`, `wbs/`, or this file is the manual substitute for the
generator that doesn't exist yet.

## Field reference (`matrix.json`)

<!-- JSON has no table to put a legend under, but the same principle applies: every field here
     must be documented so someone with no context on this feature can read a raw entry cold. -->

| Field | Meaning |
|---|---|
| `id` | Acceptance Criterion ID — the anchor of this whole matrix. |
| `criterion` | Abbreviated statement; full text is authoritative in `req/index.md §6`, not here. |
| `priority` | MoSCoW, copied from `req/index.md`'s AC table. |
| `relatedUC` | From `req/index.md`'s AC table's `Related UC` column. |
| `specComponents` | Every `spec/components/*.md` whose own `Addresses:` field cites this AC. |
| `wbPhasesViaComponents` | For each `specComponents` entry, the WB phase whose tasks actually create/modify that file — in this hand-built example, derived by reading task outcomes; a real generator would need this derivable deterministically from `wbs/index.json`'s own data (see "Open questions"). |
| `wbPhasesViaUC` | For each `relatedUC` entry, every WB phase whose `sourceUC` array (in `wbs/index.json`) includes it. |
| `gate1Covered` | AC exists in `req/` and is addressed by ≥1 `spec/` component (the check already shown in `spec/index.md §3`). |
| `gate2Covered` | AC is realized by ≥1 WB phase, cross-checked via *either* `wbPhasesViaComponents` or `wbPhasesViaUC`. |
| `gate2Kind` | Present only for AC-08/AC-09 — marks them as a structurally different kind of Gate 2 check (see Finding 3 below); absent (not `null`) for the other seven entries. |

> **Legend:** same table-legend convention used everywhere else in this feature's docs, applied
> to a JSON field list instead of a Markdown table column list — the principle (no reader should
> have to guess what a field means) doesn't change just because the data moved to JSON.

## Findings from building this example

1. **Caught a real assignment error.** `US-02`'s `sourceUC` (in `wbs/index.json`) was originally
   `["UC-02", "UC-05"]`. Building this matrix's `wbPhasesViaComponents` for AC-02 showed `US-02`
   is not among them — `US-02` only wires `wb-validate.js` (serves `UC-05`'s full post-assembly
   pass); `UC-02`'s pre-dispatch check calls `wb-graph-checks.js` directly from `pm-phase2.js`
   (`US-04`), never through `wb-validate.js`. Fixed to `sourceUC: ["UC-05"]`. This is the kind of
   error the matrix exists to catch — it would not have surfaced from reading `req/` or `spec/`
   in isolation.

2. **The two coverage paths (`wbPhasesViaComponents` vs. `wbPhasesViaUC`) diverge systematically
   for AC-04..AC-07, and the divergence is explainable, not a bug.** Both paths always *agree*
   that the AC is covered (`gate2Covered: true` either way), but *which phases* they name
   differs:
   - They disagree on `INFRA`: the UC-path can never name `INFRA` (it has `sourceUC: []` by
     design — shared infrastructure isn't owned by one UC, same reasoning as a Business Rule
     applying to "All UCs"). The component-path *can* name it, correctly, whenever the
     addressing component (e.g. `wbs-assembler.js`) happens to live there.
   - They disagree on `US-02` vs `US-05`: `UC-05` ("Assemble **and** Validate/Render Unchanged")
     bundles two actually-independent mechanics — validating (`US-02`'s territory) and rendering
     (`US-05`'s territory) — at one UC granularity. An AC that's specifically about only one of
     them (AC-04 is validate-only, AC-05 is render-only) can't be disambiguated by the UC-path
     alone; it always returns both phases `UC-05` touches. The component-path is precise here
     because `Addresses` is declared per-component, not per-UC.
   - **Conclusion: `wbPhasesViaComponents` is the authoritative source for Gate 2 coverage;
     `wbPhasesViaUC` is a secondary cross-check**, useful for catching errors like #1 above, not
     a replacement. A future revision might split `UC-05` into two UCs to close this gap at the
     source instead of working around it downstream — not done here, out of scope for an example.

3. **Gate 2 for AC-08/AC-09 is a different kind of check than AC-01..07** — marked via
   `gate2Kind` rather than silently reusing the same boolean semantics. AC-08 is satisfied by
   *absence* (no task touches the named files) — there's no positive deliverable to point a
   phase at; "all phases" really means "verified by inspecting the whole task set, not any one
   task" (`gate2Kind: "verified-by-omission"`). AC-09 is satisfied by the *aggregate* of every
   test task across every phase, not any single one (`gate2Kind: "aggregate-across-test-tasks"`).
   Both are structurally different from the other seven ACs and would need a different (simpler)
   check than "does ≥1 phase/component address this" — probably just "is this AC's text itself a
   universal/All-UCs guarantee, and if so, skip the per-phase lookup entirely and treat it as
   self-evidently in scope."

## Open questions

- `wbPhasesViaComponents` needs a deterministic source once there's a real generator —
  "which WB phase's tasks modify file X" isn't a stored fact anywhere today (not even in
  `wbs/index.json`); it was derived here by reading task `outcome` text by hand. Options: add it
  as a stored field somewhere (e.g. a `modifiesFiles` list per task, mirroring how
  `acceptanceCriteria` is already a stored per-task field), or have the generator re-derive it
  by scanning task outcomes with a convention-based heuristic (fragile) each time it runs.
- What exactly *blocks* a gate vs. what's a non-blocking warning once `coverage-check.js` is
  real? (e.g. is the AC-04/05 divergence in Finding 2 below something the generator should flag
  even though both paths agree on `gate2Covered: true`, or is agreement enough to stay silent?)
- Does the generator run as its own pipeline step (like `wb-validate.js`/`wb-render.js` are two
  separate scripts orchestrated by `pm-phase2.js`), or as one combined `coverage-check.js`
  covering both the Gate 1 and Gate 2 computation? Not decided — out of scope until this
  reaches an actual FTR (see the Phase A/B/C/D sequencing in the linked idea doc).
- Not addressed here: whether individual WB **tasks** (not just phases) should also cite ACs via
  their own `acceptanceCriteria` field, which is where `wb-validate.js`'s existing AC-scope check
  (check 20) would apply. Attempting that during this exercise surfaced that the current
  phase↔UC numbering doesn't cleanly support task-level AC scoping for `US-04` (an AC scoped to a
  single UC can't legally be cited by a task whose phase's `sourceUC` includes that UC alongside
  three others, under today's check-20 semantics) — left as a separate, unresolved design
  question rather than forced through for this example.
